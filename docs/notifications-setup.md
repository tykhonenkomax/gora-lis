# Надсилання заявок у Telegram та email

Форма викликає Supabase Edge Function `submit-booking`. Публічна частина не містить токена бота, SMTP-пароля чи service-role ключа. Справжнє підтвердження «Заявку надіслано» показується після успішного приймання повідомлень обома сервісами. Бронювання в календарі створює власник окремо.

## Підключення

1. У UKR.NET: **Налаштування → Безпека → Керування IMAP-доступом → Створити пароль**, назва `GoraLis сайт`. Потрібен саме пароль зовнішньої програми, а не пароль входу в скриньку. SMTP: `smtp.ukr.net:465`, TLS, логін `goralis@ukr.net`.
2. У Supabase створіть Personal Access Token із правом керування цим проєктом.
3. У корені проєкту створіть `.env.deploy.local`:

   ```dotenv
   SUPABASE_ACCESS_TOKEN=ваш_токен_керування
   SMTP_PASSWORD=пароль_зовнішньої_програми
   ```

4. Параметри бота містяться в локальному `.env.notifications.local` (не в Git). На іншому комп’ютері додайте до `.env.deploy.local` також `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `SMTP_USER`, `BOOKING_EMAIL`, `ALLOWED_ORIGINS`. Для цієї групи ID — `-5530761297`. `ALLOWED_ORIGINS` — перелік точних адрес джерел через кому, без шляхів; для GitHub Pages: `https://tykhonenkomax.github.io`. Новий домен Netlify потрібно додати окремо.
5. Запустіть `node scripts/deploy-notifications.mjs`. Скрипт застосовує `supabase/notifications.sql`, записує секрети в Supabase та публікує функцію без Docker.
6. Надішліть одну явно тестову заявку. Перевірте Telegram-групу й пошту (також папку «Спам»). Успішне SMTP-приймання не гарантує потрапляння саме до «Вхідних».

Якщо CLI недоступний, SQL можна виконати через SQL Editor, секрети додати в Edge Functions → Secrets, а функцію розгорнути через Supabase CLI на іншому комп’ютері. `booking.sql` повторно запускати не потрібно.

## Поведінка

- Мінімум 2 ночі; валідація на клієнті, сервері й для нових/оновлених бронювань у базі. Старі записи не видаляються.
- Сервер перевіряє гостя, телефон, будинок і дати та сам обчислює ціну. Для Atmosfera понад 4 гостей додається 500 грн за людину за ніч.
- Перед прийманням нової заявки перевіряється поточна зайнятість, включно з попередніми бронюваннями.
- Підтверджена заявка не резервує дати автоматично; двоє гостей можуть подати заявки на той самий ще вільний період.
- ID заявки зберігається в пам’яті форми до зміни її даних. При повторному натисканні після помилки доставлений канал не надсилається повторно, якщо його успіх уже записаний у базі. Оновлення сторінки створює нову заявку.
- Якщо один канал не спрацював, користувач бачить помилку з можливістю повторити або подзвонити. Повтор відновлює доставку лише недоставленого каналу. Автоматичної фонової черги повторів немає.
- Між фактичним прийняттям провайдером та записом результату можливий мережевий збій, тому абсолютної гарантії відсутності повторних повідомлень немає. У кожному повідомленні є однаковий номер заявки для розпізнавання повтору.
- Таблиця `booking_requests` доступна лише серверу; ім’я й телефон не віддаються гостьовому календарю. Для підтримки доставки адміністратор Supabase може переглянути `telegram_sent` та `email_sent`.
- Є ліміт 5 нових заявок за 10 хвилин з однієї IP-адреси та 30 за хвилину загалом; зберігається хеш IP, а не сама адреса. Поле-пастка й перевірка Origin доповнюють ці ліміти.
- Секрети зберігаються лише в Supabase та `*.local`. Не додавайте їх до `VITE_*` чи GitHub Pages.

## Перевірки

`pnpm test`, `pnpm build`, `pnpm lint`. Серверна логіка й повторні відправлення перевіряються з тестовими сервісами; фактичний SMTP і Telegram перевіряються після розгортання та налаштування секретів.
